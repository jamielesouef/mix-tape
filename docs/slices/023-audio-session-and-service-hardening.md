# 023 — Audio session and service hardening

← [previous](022-direct-stream-url.md) · [Master Checklist](MASTER-CHECKLIST.md) →

> **Status, owner and blockers live in the master checklist, not here.** Dependencies live in this page's front matter and nowhere else. Each fact has one home; if you find yourself writing it twice, one of the two copies is going to be wrong in a fortnight.

## 1. Objective

Five hardening items land together because each is a small, independent finish on a service or controller the codex round otherwise leaves as-is: audio-session interruptions/route changes/media-services reset and video's own `.playback` category, `ImageService`'s cache cost and coalescing, `LibraryService`'s pagination-failure and refresh-invalidation behaviour, request coalescing for tracks and series, and the Triage 24 audio HLS fallback URL. Observable on its own: a phone call interrupts music and it resumes after; plugging in headphones does not silently keep routing to the speaker; playing a video with the ringer silenced does not stop the audio; a slow later page of a long library keeps the pages already shown instead of blanking them; the non-native-container audio fixture from 019's evidence (`Non Native/1. Opus Test.opus`) plays instead of failing with the 400 Triage 24 found.

## 2. Business Value & Priority

None of these five is a live disclosure risk or a reproduced on-screen failure the way 020's and 021's findings are — codex marks the audio-session and image items "Medium," and the library items "Smaller." P2, and last in the delivery order, because each depends on an owner or a mechanism the earlier four slices in the round define (020's teardown owner, 021's generation), and because it is the widest single slice in the round: five unrelated subsystems, none of which unlocks value for the others. Kept as one slice rather than five because none is currently a version ladder or a claimed §1/§12 requirement — see §7 for the honest call on splitting it further.

## 3. Scope

**In scope:**

- **Audio-session lifecycle, the interruption/route/reset half** (`didConfigureSession`'s ordering was already fixed in 019) — `AudioPlayerController` observes `AVAudioSession.interruptionNotification`, `.routeChangeNotification` and `.mediaServicesWereResetNotification`. An interruption begin pauses playback through the existing `MusicPlayerService.pause()` path (the controller calls `onRemotePause`-equivalent, not a new callback — see decision log); an interruption end with `.shouldResume` resumes through the existing `onRemotePlay` path. A route change whose reason is `.oldDeviceUnavailable` (headphones unplugged) pauses, matching system convention for media apps. A media-services reset rebuilds the `AVAudioSession` configuration and, if a track was loaded, reloads it. **Every notification name and behaviour is confirmed against `apple-docs` before being written into code — this slice's implementer does not carry an API shape from memory or from this document's prose.**
- **Video's own `.playback` category** — `AVPlayerController` (and, if VLCKit needs its own activation, `VLCPlayerController`) establishes `AVAudioSession .playback` on load, independent of whether music has already configured the session, so a video played before any music is played still ignores the Ring/Silent switch. Confirmed against `apple-docs` per the row above.
- **`ImageService` cache cost, coalescing, validation** — cache cost is set from the *decoded* image's pixel dimensions (width × height × 4 bytes), not the compressed network byte count; concurrent requests for the same URL are coalesced into one in-flight task rather than firing the network request twice; the HTTP response is validated (2xx) before decoding; `preparingForDisplay()` (confirmed against `apple-docs`) is awaited before the image is handed back, so the first paint is not the decode.
- **`LibraryService` pagination-failure behaviour** — `loadMore(libraryID:)`'s catch no longer writes `pages[id] = .failed(...)` over the already-loaded, already-displayed items; it leaves `pages[id]` as the accumulated `.loaded` page and surfaces the failure through a separate, additive signal (a per-library "load more failed" flag or an `.loaded` page with a trailing error the view can show inline — decided in §6) so a library with fifty of two hundred items showing does not blank to a failure screen because item 51 timed out.
- **Refresh invalidates in-flight requests, general case** — `LibraryService.refresh()` and `SeriesService.refresh()` bump the same `OperationGeneration` type 021 introduced (reused by name and type, not reimplemented), and every in-flight load's post-`await` write is guarded by it, closing "an old response can repopulate a freshly cleared cache" for the case that is not a sign-out. This is **additive to, not a replacement for,** 020's session-identity guard: the two guards close different races at the same write site — session identity catches a write from a session that has since ended (sign-out/expiry), generation catches a write from an operation that has since been superseded within the *same* session (a plain pull-to-refresh racing a page load, which session equality alone cannot see, since the session never changes across a refresh). Both checks run at every write site 020 already guards; see the decision row below.
- **Duplicate-request coalescing for tracks and series** — `LibraryService.loadTracks(albumID:)` and `SeriesService.loadSeasons(seriesID:)`/`.loadEpisodes(seriesID:seasonID:)` each track their own in-flight requests with a new set keyed by albumID/seriesID — not one `Set<String>` per method reused from `loadLibrary`/`loadMore`, which actually share a single `Set<String>` keyed by library id (`LibraryService.swift:24`) rather than one set per method — so two views asking for the same album's tracks or the same series' seasons within the same load do not fire two network requests.
- **Triage 24** — the audio HLS fallback (decision 23; `JellyfinPlaybackRepository.audioStream`) stops requesting `/Audio/{itemId}/universal` for a non-native container and instead requests `/Audio/{itemId}/main.m3u8` directly, with the client's own query (`mediaSourceId`, `playSessionId`, `deviceId`, `audioCodec=aac`, `segmentContainer=ts`, `ApiKey`) — the pinned spec's `GetVariantHlsAudioPlaylist` operation declares `segmentContainer`, not `transcodingContainer`; the latter would be silently ignored server-side. `audioStream` gains a `playSessionID` parameter for this, sourced from the same value `MusicPlayerService` already generates and sends in its `PlaybackReport` (`MusicPlayerService.swift:49,189`) — `audioStream(track:session:)` takes no such parameter today, and the URL's value must match what is already reported, or the server's transcode-session correlation on stop breaks. This is the fix 019 §6's decision row specifies as alternative (a), which the pinned spec confirms is a real, separately-documented endpoint distinct from the master-playlist-returning `universal` endpoint whose `TranscodeReasons` join breaks Kestrel. The fix stays inside `MixtapeData`/`MixtapeUseCase` — no `AVAssetResourceLoaderDelegate`, no custom URL scheme, no resource loader of any kind (rejected already in 019's row (b) and in Triage 6).
- **The stalled-player half of Triage 24** — 019's evidence recorded that while the 400 was silently failing the HLS child fetch, `MusicPlayerService.status` stayed `.playing` and the server kept seeing a rising reported position for a player that was not actually advancing. Once the URL fix above removes the 400 for the fixture that exposed it, this slice adds one narrow guard so a *future* stalled player (any cause — a genuinely broken HLS variant, a network stall) is not silently mis-reported forever: `MusicPlayerService`'s existing clock-driven periodic task (`MusicPlayerService.swift:246-254`, the same loop that already refreshes now-playing and reports every second tick per Triage 21) treats a run of ticks with no `position` advancement while `status == .playing` as a failure and routes it through the same failure path the controller's own `onFailure` callback already uses — armed only after `position` has first advanced past zero, so initial buffering before the first tick is not mistaken for a stall. See the decision log for why this sits in `MixtapeServices`, not `MixtapeInfrastructure`.

- **Triage 26 — the natural-end race** — `MusicPlayerService.trackDidEnd()` wraps its work in a `Task` that reads `currentIndex` when it runs, not when the controller's `onEnded` fired, so a Next pressed as a track ends can advance twice. The callback captures the ending track's identity (and the current `OperationGeneration`) at the moment `onEnded` fires and acts only if that track is still current when the `Task` runs. Raised by 021's implementer; recorded in the master checklist as Triage 26.

**Out of scope** (name the slice it's deferred to):

- Anything already closed by 019: `didConfigureSession`'s success-only assignment, VLC log redaction, artwork retention, keychain update-then-add, video scrubber drag-hold, Reduce Transparency opacity, header escaping, "Change server".
- Session-owned teardown itself (020) and playback operation generations themselves (021) — this slice only *reuses* both.
- Direct-stream URL construction (022).
- Observing the server's actual `PlayMethod`/playback decision instead of inferring it — recorded, no change, per 019's disposition table; unaffected by this slice's HLS URL change (the inference logic in `isNativeAudioContainer` is unchanged, only the fallback URL is).

**Plan requirements covered:** none. Defect and hardening work, gated on builds, tests and the scripts, plus each item's own demonstration. This slice amends decision 23's endpoint (`universal` → `main.m3u8` for the fallback case only) by an appended `SPEC-DECISIONS.md` row, per the decision log below — not a silent departure.

## 6. Decision Log

**Write the row before you implement the decision, not after.**

| Date | Decision | Alternatives rejected | Why |
|---|---|---|---|
| 2026-09-07 | Interruptions and route changes are routed through the *existing* pause/resume seam — `AudioPlayerController` calls the same closures it already exposes for a remote pause/play (`onRemotePause`/`onRemotePlay`), not a new callback pair, so `MusicPlayerService` needs no new method to react to them. | A new `onInterruptionBegan`/`onInterruptionEnded`/`onRouteChanged` callback triple on `AudioPlayerControlling`, handled separately from remote-command pause/resume in `MusicPlayerService`. | An interruption pause and a remote-command pause are the same thing from the service's point of view — the player stopped for a reason outside the app, and the service's existing `pause()`/`resume()` already does exactly what's needed (stops the report loop's cadence assumptions, updates `status`, refreshes now-playing). A second pair of callbacks would duplicate that logic for no behavioural difference. |
| 2026-09-07 | Video establishes `.playback` on its own controller's `load`, independent of whether `AudioPlayerController` has ever run. Video never calls `AVAudioSession.setActive(false)` — only `AudioPlayerController` calls `setActive(true)` today (`AudioPlayerController.swift:119`) and nothing calls `setActive(false)` anywhere; this slice's video controller follows the same policy (activate, never deactivate) rather than introducing a deactivation call that would silence a concurrently playing album. | A single shared audio-session-configuration function called by whichever controller loads first, with the other skipping it once `didConfigureSession`-equivalent is true. Also rejected: video calling `setActive(false)` on its own teardown, symmetrical with its `setActive`-on-load. | Sharing one flag between two controllers that can each be torn down and rebuilt independently (video's controller is created and torn down per `VideoPlaybackService.play()`/`.stop()`; audio's is a single long-lived instance) means the flag's truth depends on which controller happened to run first this launch — exactly the kind of hidden cross-controller coupling CLAUDE.md's "no `.shared`, no service locator" rule exists to keep out. Each controller owns its own session activation; `AVAudioSession.setCategory` is idempotent for the same category, so there is no cost to both calling it. `setActive` is not idempotent the same way: the audio session is shared process-wide, so video deactivating it on its own teardown would silence music if a track happened to be playing underneath — the exact cross-controller coupling this row's main decision otherwise avoids. |
| 2026-09-07 | The `OperationGeneration` check this slice adds to `LibraryService`/`SeriesService`'s `refresh()` **supplements** 020's session-identity guard at each write site — both checks run, neither replaces the other. | Having the generation check replace the session-identity guard outright, so each write site carries one guard, not two. | Session identity and generation close two different races and neither subsumes the other: session identity is the only guard that can tell "a sign-out/expiry happened," since the session value itself changes then and does not change across a same-session `refresh()`; generation is the only guard that can tell "a newer operation superseded this one within the same session," which is exactly the case a plain pull-to-refresh racing a page load needs and session equality cannot see (the session never changes). Replacing 020's guard with only a generation would reopen the sign-out race 020 closed unless `endSession()` were also made to bump the generation — at which point the two mechanisms have been fused into one anyway, at greater cost than running both existing checks at each write site. 021's pre-flight bullet and row 1 already anticipated this reuse ("named for what it guards... so 023 can reuse the same type... without the name implying playback"); this row is the explicit statement 021 deferred to 023. |
| 2026-09-07 | `LibraryService`'s pagination-failure signal is a new field, `pageLoadError: [String: MixtapeError]`, set on a `loadMore` failure and cleared on the next successful `loadMore` or on `refresh()`; `pages[id]` itself is never overwritten by a `loadMore` failure. | (a) Encode the failure inside `LoadState<Page<MediaItem>>` itself, e.g. a new `.loadedWithTrailingError` case. (b) Silently drop the failure with no visible signal at all. | (a) changes `LoadState`'s shape, which `MixtapeDomain` and every other caller of `LoadState` (details, tracks, continueWatching) would need to account for, for a case only `pages` has; a sibling dictionary keyed the same way as `pages` costs one field and touches nothing else. (b) is worse than codex's own finding — it turns "blanks the list" into "silently stops paginating with no way for the view to know," which is not a fix, it is the same defect with the visible half removed. |
| 2026-09-07 | Triage 24's fix requests `/Audio/{itemId}/main.m3u8` directly (`GetVariantHlsAudioPlaylist`, confirmed present and separately documented in the pinned spec) in place of `/Audio/{itemId}/universal` for the non-native-container case, keeping every other query parameter `JellyfinPlaybackRepository.audioStream` already sends and adding two: `mediaSourceId` (not sent today) and `playSessionID`, sourced from the same value `MusicPlayerService` already generates and sends in its `PlaybackReport` — `audioCodec=aac`, `segmentContainer=ts` (not `transcodingContainer`, which this endpoint does not declare), `deviceId`, `ApiKey` carry over. This amends decision 23's endpoint choice for the fallback branch only — the native-container branch is unaffected. The implementing commit appends a new `SPEC-DECISIONS.md` row stating: *"decision 23's HLS fallback for a non-native audio container requests `/Audio/{itemId}/main.m3u8` directly rather than `/Audio/{itemId}/universal`, because the `universal` endpoint's master playlist joins `TranscodeReasons` with unencoded spaces that Kestrel rejects with 400 before Jellyfin logs anything (Triage 24, closed by 019's cause row and 023's fix); `main.m3u8` is the child variant playlist the master would otherwise have pointed at, requested with the client's own query (including `playSessionID`, threaded through for the first time), so its own segment URIs inherit a space-free query the way 019's reproduction showed for a raw `%20`-encoded request."* | Rewriting the master playlist in flight (rejected already in 019 as the resource-loader approach Triage 6 rejected) or reporting the finding upstream and waiting (019's rejected alternative (c), still not a client fix). | Both were already measured and rejected in 019; this row exists so a reader of 023 alone does not have to reopen that comparison — it is restated, not re-decided. |
| 2026-09-07 | The stalled-player guard is a position-advancement watchdog inside `MusicPlayerService`'s existing clock-driven periodic task (the same 5 s-tick loop Triage 21 already added for now-playing refresh and reporting): if `status == .playing`, `position` has already advanced past zero at least once, and no further advancement is observed for a fixed number of ticks, the service routes the condition through the same failure path the controller's own `onFailure` callback already uses. | (a) A watchdog inside `AudioPlayerController` instead, riding the controller's own periodic time observer and calling `onFailure` directly — this row's own first draft. (b) No "already advanced past zero" arming condition, checking staleness from the first tick. | (a) is the currently-rejected choice: `AudioPlayerController` is Infrastructure, which per fork F1 has no unit test target of its own — only a demonstration. `AC23h` requires a `MixtapeServicesTests` assertion using a stub `AudioPlayerController` and `ManualClock` proving the watchdog fires; a stub built to satisfy that would have to implement the watchdog logic itself, testing the stub's own plumbing rather than production code. `MusicPlayerService` already observes callback staleness identically via its own injected clock (`MusicPlayerService.swift:59,69`) and existing periodic task (`:246-254`), so the mechanism this row describes already has a home with a real test target — nothing about the watchdog needs the controller's own time-observer interval specifically, only that ticks stop advancing `position`. (b) would misreport a track that is still buffering before its first `onPositionChange` as stalled; arming only after the first advancement avoids that false positive. |

## 7. Sub-Slices

Not split — delivered as a single slice, with the size and the fallback plan recorded honestly here rather than glossed over.

The template's only stated split trigger (§7, "Split with `NNNa`, `NNNb`") is illustrated for version ladders, and this slice is not one — `ladder: none`. Nothing in the template makes size alone a mandatory split condition. All five items share the same position at the tail of the codex round, so a split would multiply front matter and `depends_on` rows without changing what any one part unlocks — none of the five items unlocks value for any other.

That said, P2/L is an honest description, not a comfortable one. If CLAUDE.md's "gate fails twice in a row with no progress" rule fires during this slice, the five bullets in §3 are already a clean split line — `023a` (audio-session interruptions/route/reset + video `.playback` category), `023b` (`ImageService`), `023c` (`LibraryService`/`SeriesService` pagination, refresh invalidation, coalescing), `023d` (Triage 24 HLS URL + stalled-player watchdog) — each a full slice doc with `parent_slice: "023"`, each keeping the `depends_on` rows above. Not built now; recorded so a stalled implementation has a pre-agreed fallback rather than an improvised one.
