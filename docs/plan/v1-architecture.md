# Mix Tape — v1 Architecture

Authoritative for Phase 2 scaffolding and Phase 3 review. It supersedes nothing in `docs/app-architecture-template.md`; where the two disagree, the conflict is recorded in [Conflicts](#conflicts) rather than resolved silently.

## Context

Mix Tape is a self-hosted, album-centric music server and client — a Plex alternative for music, built to avoid subscriptions. The design concept is pulling a CD out of a wallet: you pick an album, it plays, it finishes, you are back at the wallet. No cross-album queue, no shuffle, no algorithmic up-next.

The repository is greenfield. At the time of writing it holds `api/` (empty), `app/` (a one-view Xcode project with Sign in with Apple entitlements already set), and `docs/app-architecture-template.md`. Nothing else exists.

This is the output of Phase 1 of a three-phase build. Phase 2 scaffolds the repository from this document. Phase 3 reviews the scaffold against it.

Three decisions were confirmed with the project owner before drafting:

- Directory names follow the handoff document: `Server/`, `App/`, `Shared/`, with `MixTape.xcodeproj`. Existing `api/` and `app/` are renamed in Phase 2.
- The six architecture layers become **six folders inside one app target**, not six build targets. This is a deliberate, approved deviation from `docs/app-architecture-template.md`, recorded in [Conflicts](#conflicts) so Phase 3 does not treat it as blocking.
- This plan lives in the repository only. There is no Obsidian mirror.

## 1. Shared DTO surface

`Shared/` is its own Swift package with **zero external dependencies**. It contains `Codable`, `Sendable`, Foundation-only types. It compiles on Linux — no SwiftData, no Observation, no Core Graphics, no Apple-only Foundation API.

### Identity

Every DTO id is a lowercase SHA-256 hex string generated by the server. `Shared` carries them as plain `String` — the hashing lives in `Server/`, which already has swift-crypto transitively via JWTKit.

| Id | Derived from | Stability |
|---|---|---|
| `AlbumDTO.id` | Canonical key `albumArtist\u{1F}title\u{1F}discNumber`, trimmed, whitespace-collapsed, casefolded | Stable across rescans while tags are unchanged |
| `TrackDTO.id` | Library-relative file path | Stable across retagging; changes if the file moves |

Album ids being tag-derived is what lets a downloaded album survive a rescan. Track ids being path-derived means a retag does not orphan a downloaded file.

### `TrackDTO`

| Field | Type | Notes |
|---|---|---|
| `id` | `String` | SHA-256 of `relativePath` |
| `albumID` | `String` | |
| `title` | `String` | Falls back to filename without extension |
| `trackArtist` | `String` | The performing artist. **Never** used for album grouping |
| `trackNumber` | `Int` | Falls back to filename sort order within the album |
| `discNumber` | `Int` | Defaults to `1` |
| `duration` | `Double` | Seconds |
| `byteSize` | `Int64` | Drives download progress and disk estimates |
| `relativePath` | `String` | Path under the music root. Also the audio URL path |

### `AlbumDTO`

| Field | Type | Notes |
|---|---|---|
| `id` | `String` | |
| `albumArtist` | `String` | **Separate from `TrackDTO.trackArtist`.** The grouping key |
| `title` | `String` | Falls back to parent directory name |
| `discNumber` | `Int` | Part of the key |
| `discCount` | `Int?` | Lets the grid label "Disc 2 of 2" |
| `year` | `Int?` | |
| `trackCount` | `Int` | |
| `totalDuration` | `Double` | Seconds |
| `hasArtwork` | `Bool` | The artwork URL is derivable from `id`; this says whether to request it |
| `tracks` | `[TrackDTO]` | Embedded. One manifest carries everything |

The `(albumArtist, title, discNumber)` key is the single most important decision in the schema. Keying on `trackArtist` explodes every compilation and every guest-feature track into a one-track album. Retrofitting it means a migration.

### `LibraryManifestDTO`

| Field | Type | Notes |
|---|---|---|
| `revision` | `String` | SHA-256 over sorted album ids, track ids and byte sizes. Served as the `ETag` |
| `generatedAt` | `Date` | ISO 8601 on the wire |
| `albums` | `[AlbumDTO]` | The whole library |

Roughly 5 MB of JSON for a 2000-album library. Served gzipped, with `ETag`/`If-None-Match` so a launch with an unchanged library costs a 304.

### `VersionResponseDTO`

| Field | Type | Notes |
|---|---|---|
| `apiVersion` | `Int` | Starts at `1`. Bumped on any breaking DTO change |
| `serverVersion` | `String` | Human-readable build string |
| `claimed` | `Bool` | Whether an owner exists yet. Drives "claim this server" vs "sign in" onboarding |

### `AuthExchangeRequestDTO`

| Field | Type |
|---|---|
| `identityToken` | `String` |

### `AuthExchangeResponseDTO`

| Field | Type | Notes |
|---|---|---|
| `token` | `String` | The server-issued long-lived token |

### `ErrorResponseDTO`

| Field | Type | Notes |
|---|---|---|
| `code` | `APIErrorCode` | Machine-readable |
| `message` | `String` | Human-readable |

`APIErrorCode: String, Codable, Sendable` — cases: `invalidIdentityToken`, `notOwner`, `unauthorized`, `notFound`, `scanInProgress`, `internalError`. American spelling in identifiers, Australian spelling in prose, per the project convention.

### `MixTapeJSON`

`Shared` also carries one small helper — `MixTapeJSON.encoder` and `MixTapeJSON.decoder`, both configured with the `.iso8601` date strategy. Foundation-only and Linux-clean. It exists so the two sides cannot drift on date encoding. This is a minor deviation from "DTOs only" and is recorded in [Conflicts](#conflicts).

### Linux-clean confirmation

Every type above is a `struct` or `String`-raw-value `enum` conforming to `Codable, Sendable, Hashable`, built from `String`, `Int`, `Int64`, `Double`, `Bool`, `Date` and arrays of those. `JSONEncoder` and `JSONDecoder` are in swift-corelibs-foundation. Nothing here is Apple-only. This is confirmed by inspection at plan time; the binding proof is Phase 2's `server.yml` CI job, which compiles `Shared` on Linux on every change.

## 2. SwiftData schema

Two model groups, one `ModelContainer`, and **no SwiftData relationship crossing between them**. They associate only by matching `id` strings, joined in memory at read time. That absence of a relationship is the whole boundary.

### Cache models — the server is the source of truth

```
CachedAlbum
  id: String              @Attribute(.unique)
  albumArtist: String
  title: String
  discNumber: Int
  discCount: Int?
  year: Int?
  trackCount: Int
  totalDuration: Double
  hasArtwork: Bool
  tracks: [CachedTrack]   @Relationship(deleteRule: .cascade, inverse: \CachedTrack.album)

CachedTrack
  id: String              @Attribute(.unique)
  title: String
  trackArtist: String
  trackNumber: Int
  discNumber: Int
  duration: Double
  byteSize: Int64
  relativePath: String
  album: CachedAlbum?
```

### Download models — local truth

```
DownloadedAlbum
  id: String              @Attribute(.unique)   same value as CachedAlbum.id
  albumArtist: String                           self-sufficient copy
  title: String
  discNumber: Int
  year: Int?
  trackCount: Int
  hasArtwork: Bool
  state: String                                 DownloadState raw value
  requestedAt: Date
  completedAt: Date?
  tracks: [DownloadedTrack]  @Relationship(deleteRule: .cascade, inverse: \DownloadedTrack.album)

DownloadedTrack
  id: String              @Attribute(.unique)   same value as CachedTrack.id
  title: String
  trackArtist: String
  trackNumber: Int
  discNumber: Int
  duration: Double
  relativePath: String                          "<albumID>/<trackID>.<ext>", relative to the downloads root
  bytesExpected: Int64
  bytesReceived: Int64
  state: String
  resumeData: Data?
  album: DownloadedAlbum?
```

`DownloadedAlbum` carries its own copy of every field it needs to render and play. It never reads a `CachedAlbum`. A downloaded album stays fully usable after a NAS rescan removes it from the manifest — it simply stops appearing in the "on server" list and keeps appearing in the "downloaded" list.

`relativePath` is stored relative to the downloads root, never absolute. The app container path changes between launches and updates; a stored absolute path is a guaranteed bug.

### How a full manifest replacement leaves downloads intact

`LibraryImporter.replaceLibrary(with:)` runs exactly this:

1. `try context.delete(model: CachedTrack.self)`
2. `try context.delete(model: CachedAlbum.self)`
3. Insert every `CachedAlbum` and `CachedTrack` from the manifest
4. `try context.save()`

It never references a `Downloaded*` type. Because no relationship joins the two graphs, no cascade can reach a download, and SwiftData has no path by which a delete on one group touches the other. Nothing reconciles, nothing merges, nothing syncs incrementally.

### `ModelActor`

`LibraryImporter` — `@ModelActor actor LibraryImporter`, at `App/AppData/Persistence/LibraryImporter.swift`. Note that `final` is not written; actors cannot be declared `final`.

Import path: `LibraryService` fetches a `LibraryManifestDTO` through `LibraryRepository`, then calls `await libraryImporter.replaceLibrary(with: manifest)`. The DTO is `Sendable` and crosses the boundary safely. **No `@Model` object ever crosses an isolation boundary.** Where an identifier must come back out it is a `PersistentIdentifier`; in practice `replaceLibrary` returns nothing, because views read the store through `@Query`.

Views use `@Query` for the album grid and the downloads list. `LibraryService` owns only sync state (`idle`, `syncing`, `failed(String)`) and the current `revision` — it does not mirror the library in memory.

The `ModelContainer` and both `Schema` groups live at `App/AppData/Persistence/`, per the template's stated exception.

## 3. API endpoints

Auth is `Authorization: Bearer <token>` except where noted. There is no path versioning — `/version` carries the API version integer.

| Method | Path | Auth | Request | Response |
|---|---|---|---|---|
| `GET` | `/version` | none | — | `VersionResponseDTO` |
| `POST` | `/auth/apple` | none | `AuthExchangeRequestDTO` | `AuthExchangeResponseDTO`, or `403` `notOwner` |
| `GET` | `/library` | bearer | — | `LibraryManifestDTO`, `ETag: <revision>`. `304` when `If-None-Match` matches |
| `POST` | `/library/rescan` | bearer | — | `202`, empty body. `409` `scanInProgress` if one is running |
| `GET` | `/artwork/{albumID}` | bearer | — | Original embedded image bytes, `ETag`, `Cache-Control: max-age=31536000, immutable` |
| `GET` | `/audio/**` | bearer **or** `?token=` | — | Audio bytes, `Range`-served by `FileMiddleware` |

`POST /library/rescan` returns immediately and does not block. A scan of a large library takes minutes; the client polls `GET /library` and sees the `ETag` change when the scan lands. This costs zero new DTOs.

`relativePath` contains slashes, so `/audio` is a **catch-all wildcard route**, not a single path parameter. In Hummingbird 2 that is `/audio/**`, and the remainder is percent-decoded and resolved against the music root. Any resolved path escaping that root is rejected with `404`.

`/artwork` and `/audio` are both served by `FileMiddleware` — artwork from the artwork cache directory, audio from the music root. `FileMiddleware` handles HTTP `Range` correctly, including multi-range and `If-Range`. Byte-range streaming is never hand-rolled.

The audio route accepts the token as a query parameter as well as a header. This exists so `AVPlayerItem` can stream a remote track without relying on `AVURLAssetHTTPHeaderFieldsKey`, which is undocumented. The trade-off is the token appearing in server access logs on a single-owner box; see [Open questions](#open-questions).

**Phase 2 verification item:** confirm that two `FileMiddleware` instances, mounted on two different roots under two different path prefixes, coexist in Hummingbird 2 and pass through to the next handler on a miss. If they do not, fall back to a single cache root with the music directory mounted beneath it.

## 4. Library scan design

### What it scans

A recursive walk of `MIXTAPE_MUSIC_DIR` for `.flac`, `.m4a`, `.mp3`, `.aac`, `.wav`, `.aiff` and `.aif`. Anything else is ignored — the server never transcodes, and AVFoundation plays all of the above natively.

### ffprobe

One `Process` per file:

```
ffprobe -v quiet -print_format json -show_format -show_streams <file>
```

Bounded `withTaskGroup`, concurrency capped at `ProcessInfo.processInfo.activeProcessorCount`. ffprobe is invoked as a bundled binary, never linked — this keeps the licence position clean.

### Tag mapping

Tags are read case-insensitively from `format.tags` first, then `streams[].tags` — FLAC and Vorbis-comment containers put them in different places.

| DTO field | Tag keys tried, in order |
|---|---|
| `albumArtist` | `album_artist`, `ALBUMARTIST`, `albumartist` |
| `trackArtist` | `artist`, `ARTIST` |
| `title` (album) | `album`, `ALBUM` |
| `title` (track) | `title`, `TITLE` |
| `trackNumber` | `track`, `TRACKNUMBER` — split on `/`, take the first part |
| `discNumber` | `disc`, `DISCNUMBER`, `disk` — split on `/`, take the first part |
| `discCount` | Second part of the `disc` tag |
| `year` | `date`, `year`, `originaldate` — take the first four digits |
| `duration` | `format.duration` (a `String`), parsed to `Double` |
| `byteSize` | `format.size` (also a `String`), parsed to `Int64` |

### Missing or malformed tags

Every case has a defined fallback. A file is never dropped for a missing tag — only for being unreadable.

| Problem | Behaviour |
|---|---|
| No album artist tag | Use `artist`. **Except:** if two or more distinct `artist` values appear in the same directory with no album artist tag anywhere in it, use the literal `"Various Artists"` for all of them. This is what keeps compilations from exploding |
| No album tag | Use the parent directory name |
| No title tag | Use the filename without its extension |
| No track number | Sort the album's files by filename and assign `1...n` |
| No disc number | `1` |
| Unparseable year | `nil` |
| ffprobe exits non-zero, or the file has no audio stream | Skip the file. Log the path. Count it in the scan's `skipped` total |

### Artwork

The preferred source is embedded: the first track in the album with a stream where `disposition.attached_pic == 1`. Extracted once per album with a stream copy, never a re-encode:

```
ffmpeg -i <file> -an -c:v copy -f image2 <cacheDir>/artwork/<albumID>.jpg
```

Falling back to `cover.jpg`, `folder.jpg` or `front.jpg` in the album's directory, copied as-is.

This is not image processing. Nothing is decoded, resized or recompressed — Linux has no Core Graphics and the server does not need one. The client downsamples with ImageIO and caches the result. It also makes `/artwork` a plain static-file route.

### Grouping

Albums are grouped on the normalised key `(albumArtist, title, discNumber)` — trimmed, internal whitespace collapsed to single spaces, casefolded for comparison. The *original* casing is what gets stored and displayed.

### Output and the index

The scan builds `[AlbumDTO]`, computes `revision`, and writes the whole `LibraryManifestDTO` to `<cacheDir>/library.json`.

`actor LibraryIndex` holds the current manifest in memory and serves `/library`. It is rebuilt at boot from the JSON snapshot and replaced wholesale at the end of a scan. GRDB only if a personal library ever outgrows this, which it will not.

### When it runs

| Trigger | Behaviour |
|---|---|
| Boot, snapshot present | Load `library.json`, serve immediately, **no scan** |
| Boot, no snapshot | Scan, then serve |
| `POST /library/rescan` | Scan in the background, replace the index and snapshot on completion |
| Filesystem watch | **Not in v1.** Adding music means hitting rescan. Cheap to add later; nothing in this design blocks it |

## 5. Auth flow

Sign in with Apple is used **once**, for pairing. It is not the session mechanism.

### The pairing exchange

1. The app presents `SignInWithAppleButton`, receives an `ASAuthorizationAppleIDCredential`, and takes its `identityToken` (a JWT).
2. The app sends `POST /auth/apple` with `AuthExchangeRequestDTO`.
3. The server fetches Apple's public keys from `https://appleid.apple.com/auth/keys`, cached in memory and refreshed when an unknown `kid` appears.
4. The server verifies the token with JWTKit: signature, `iss == "https://appleid.apple.com"`, `aud == MIXTAPE_APPLE_BUNDLE_ID`, and `exp` not passed.
5. The server extracts the `sub` claim.
6. **Ownership check**, against `<dataDir>/owner.json`:
   - File absent → write `{ "sub": ..., "claimedAt": ... }`. This first login claims the server.
   - File present, `sub` matches → proceed.
   - File present, `sub` differs → `403` with `APIErrorCode.notOwner`.
7. The server issues **its own** token: a JWT signed HS256 with a server secret, claims `{ sub, iat, jti }` and `exp` ten years out. A signed token means no token database and no per-request storage read.
8. The app stores the token in the Keychain with `kSecAttrAccessibleAfterFirstUnlock`, so a background download can read it while the device is locked.

### The server secret

Taken from `MIXTAPE_TOKEN_SECRET` if set. Otherwise generated on first boot and written to `<dataDir>/secret` with mode `0600`. Rotating or deleting that file invalidates every issued token — that is the revoke story, and it is the whole revoke story for v1.

### Every subsequent request

`Authorization: Bearer <token>`. Middleware verifies the HS256 signature, then checks that `sub` still equals the owner's `sub`. Two cheap checks, no I/O.

Apple's identity token is deliberately never used as the session token. It is short-lived, and refreshing it needs server-to-server calls with a client-secret JWT that Apple caps at six months — an indefinite rotation chore on a box in a cupboard.

### Second device

The same Apple ID produces the same `sub`, so a second device pairs successfully and receives its own independent token. There is no device list, no device limit, and no revoke-one-device story in v1. A **different** Apple ID is refused with `notOwner`. Sharing a library with another person is out of scope.

### Configuration

`MIXTAPE_APPLE_BUNDLE_ID` is required — every self-hoster builds the app with their own signing team and bundle ID, so it can never be hardcoded.

`MIXTAPE_APPLE_TEAM_ID` is **not** required to verify an identity token; it is only needed to generate a client secret, which this design deliberately avoids. The handoff document asks for both to be configuration. Recorded in [Conflicts](#conflicts).

## 6. Download lifecycle

### States

`DownloadState: String` — `queued`, `downloading`, `completed`, `failed`.

Stored on `DownloadedTrack` per track. `DownloadedAlbum.state` is recomputed and stored whenever a track changes, so the grid can query it directly: any track `failed` → `failed`; any `downloading` → `downloading`; all `completed` → `completed`; otherwise `queued`. A user-facing pause is not in v1.

### Where the files live

```
Application Support/MixTape/Downloads/<albumID>/<trackID>.<ext>
Application Support/MixTape/Downloads/<albumID>/artwork.jpg
```

The `Downloads` directory is marked `isExcludedFromBackupKey = true`. The content is re-downloadable and must not bloat a user's iCloud backup.

Only the path *relative to* `Downloads/` is ever stored in SwiftData.

### The background session

One `URLSession`, created once and owned by `DownloadService`:

- `URLSessionConfiguration.background(withIdentifier: "io.mixtape.downloads")`
- `isDiscretionary = false`
- `sessionSendsLaunchEvents = true`
- `Authorization: Bearer <token>` set on each `URLRequest`. Because the server token has a ten-year expiry, a download queued days ago and resumed after relaunch still authenticates. This is a direct payoff of not using Apple's short-lived token.

Each task carries `taskDescription = trackID`. That string survives an app relaunch, so task-to-track mapping needs no shared dictionary and no state that could be lost.

### The delegate shim

`DownloadSessionDelegate` at `App/AppServices/Download/DownloadSessionDelegate.swift` — a `final class NSObject, URLSessionDownloadDelegate`, `nonisolated`.

`urlSession(_:downloadTask:didFinishDownloadingTo:)` hands over a temporary file URL that is valid **only for the duration of the callback**. The delegate therefore performs `FileManager.moveItem` synchronously on the delegate thread, and only then hops:

```
Task { @MainActor in await downloadService.trackFinished(trackID: id, at: destination) }
```

This is the concurrency friction point the handoff predicts. It is the one place a `nonisolated` shim is justified, and the justification is written in the file. There is no `@unchecked Sendable` and no `DispatchQueue`.

### Resuming after relaunch

- The scene declares `.backgroundTask(.urlSession("io.mixtape.downloads"))`.
- On launch, `DownloadService` recreates the session with the same identifier; the system reattaches the in-flight tasks and replays any delegate calls that happened while the app was dead.
- Reconciliation: `session.getAllTasks()` is compared against SwiftData. Any row in `downloading` or `queued` with no live task is marked `failed` and re-enqueued, using `resumeData` when it is present.

### How playback chooses local over remote

`PlaybackService.load(album:)` builds one `AVPlayerItem` per track:

1. Look for a `DownloadedTrack` with that `id` in state `completed`.
2. If found **and** the file exists on disk, use `AVPlayerItem(url: <local file URL>)`.
3. Otherwise use `AVPlayerItem(url: <server audio URL with ?token=>)`.

The disk existence check matters — iOS can evict files, and a SwiftData row saying `completed` is not proof the bytes are still there. A missing file falls back to streaming and flips the row to `failed` so the UI can offer a re-download.

### Playback rules

The queue **is** the album. Loading an album replaces the `AVQueuePlayer` queue entirely. Next on the final track stops playback and does nothing else — it never advances to another album. That is the CD-wallet concept, not an oversight, and it gets a comment in the source so nobody "fixes" it.

`AVAudioSession` category `.playback` plus the background audio capability, or playback stops on lock. `PlaybackService` feeds `MPNowPlayingInfoCenter` and `MPRemoteCommandCenter`.

### The six layers, as folders

### Server

Hummingbird 2, structured-concurrency native. Direct play only — the server never transcodes. `FileMiddleware` handles all `Range` work.

### Build

Multi-stage `Dockerfile`, build context at the repository root, dependencies resolved before sources are copied so a source edit never re-fetches Hummingbird. `--static-swift-stdlib`, so the runtime image needs ffmpeg and nothing else. Single architecture, matching the target NAS.

The build stage is `swift:6.2-noble`, **not** the `swift:6.1-noble` in the handoff document. `Shared` compiles under both the server and the app, so one Swift language level covers the whole repository. See [C5](#c5--swift-61-in-the-dockerfile-vs-swift-62-in-the-template-resolved-by-the-project-owner).

**Docker is a packaging step, not a dev loop.** `swift run Server` on macOS runs the identical binary against a local music folder with the app pointed at `localhost`. The Linux CI job is what catches Apple-only API that slipped in.

CI path filters: `server.yml` on `Server/**` and `Shared/**`; `app.yml` on `App/**` and `Shared/**`. A DTO change fires both. A SwiftUI change fires neither server job.

### Licensing

| Path | Licence |
|---|---|
| `Shared/` | MIT |
| `App/` | MIT |
| `Server/` | AGPL-3.0-only |

`Shared` must be permissive. MIT flows into AGPL; AGPL does not flow into MIT. An AGPL `Shared` would make the MIT client claim invalid. Four `LICENSE` files — one per directory plus a root one explaining the split — `SPDX-License-Identifier` as the first line of every source file, and `CONTRIBUTING.md` with DCO sign-off rather than a CLA.

## Conflicts

The handoff document names `docs/app-architecture-template.md` as authoritative for app architecture and requires conflicts to be flagged, not silently resolved. These are the conflicts found.

### C1 — Six targets vs six folders *(resolved by the project owner)*

The template says six build targets. The handoff's own "no abstraction without a second conformer" rule and a four-service v1 pull the other way. **The project owner chose six folders inside one app target.** Every other template rule is kept, and `scripts/check-layer-imports.sh` enforces the boundary by path. Phase 3 must treat this as approved, not blocking.

### C2 — `private actor` fetcher inside a service vs repositories

The handoff describes `LibraryService` as holding "a `private actor` fetcher for network calls". The template puts networking in `AppInfrastructure` (an `APIClient` actor) and `AppData` (stateless `Sendable` repository structs), and forbids a repository or use case type appearing in a view's signature.

**Following the template:** `APIClient` is the actor, `LibraryRepository` is the stateless struct, and `LibraryService` holds no private actor. The handoff's intent — that network work is off the main actor behind an actor boundary — is fully preserved.

### C3 — Repository protocols vs "no abstraction without a second conformer"

Phase 3 is told to flag any protocol without a second conformer. The template mandates repository protocols in `AppUseCase` and, in the same document, requires every use case and service to be tested against injected `Mock*`/`Stub*` doubles. Those doubles **are** the second conformer. This is recorded so Phase 3 does not raise it as a finding.

### C4 — `Shared` is "DTOs only", but carries `MixTapeJSON`

`Shared` gains one non-DTO type: `MixTapeJSON`, holding a configured `JSONEncoder` and `JSONDecoder`. Foundation-only and Linux-clean. It exists so the two sides cannot drift on date encoding strategy. A small, deliberate deviation.

### C5 — Swift 6.1 in the Dockerfile vs Swift 6.2 in the template *(resolved by the project owner)*

The handoff's Dockerfile uses `swift:6.1-noble`; the template requires Swift 6.2 and Swift 6 language mode. Server and app compile separately, so 6.1 would have been legal — but `Shared` compiles under **both**, which would have pinned `Shared` to the lower language level.

**Resolved: the Dockerfile build stage uses `swift:6.2-noble`.** One language level covers the whole repository. Phase 2 must not copy the handoff's `swift:6.1-noble` line verbatim.

### C6 — Team ID configuration is unused

The handoff requires Team ID and bundle ID to be configuration. Verifying an Apple identity token needs only the bundle ID, as the `aud` claim. Team ID is needed solely for generating a client secret, which this design deliberately avoids. `MIXTAPE_APPLE_TEAM_ID` is documented in `docker-compose.yml` but read by nothing in v1.

### C7 — Ogg Vorbis

Out of scope, as stated. Recorded here so it is a decision on the record rather than an omission.

## Open questions

1. **Multi-disc albums each get their own wallet slot.** Keying on `(albumArtist, title, discNumber)` means "Disc 1" and "Disc 2" appear as two separate tiles in the grid. That is arguably exactly right for a CD-wallet concept — one physical disc, one slot — but it is worth confirming rather than assuming. The alternative is grouping discs under one album and keying tracks on `(discNumber, trackNumber)`. **This affects the schema and cannot be changed later without a migration.**

2. **Audio auth: query parameter or header.** The plan uses `?token=` on `/audio` so `AVPlayerItem` can stream without `AVURLAssetHTTPHeaderFieldsKey`, which is undocumented. The cost is the token appearing in access logs on a single-owner box. The alternative is header-only, accepting the undocumented API.

3. **Default album grid ordering.** Album artist then year? Album artist then title? Recently added? v1 needs exactly one default and no sort control.

4. **Placeholder for albums with no artwork.** Not specified anywhere. Needs a decision before `AlbumGridScreen` is built.

5. **Server directory layout.** One bind-mounted volume for both data (`owner.json`, `secret`) and cache (`library.json`, extracted artwork), or two? One is simpler; two lets a user wipe the cache without losing the server claim.
